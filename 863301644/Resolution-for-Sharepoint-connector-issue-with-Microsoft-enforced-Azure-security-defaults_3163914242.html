Magic Global Support : Resolution for Sharepoint connector issue with Microsoft-enforced Azure-security defaults

Created by Vinayak Dane, last modified on 27,Jan, 2025

Microsoft has begun disabling legacy authentication methods, including App passwords, in favor of modern protocols like OAuth2 and OpenID.

Concern:

This change has caused problems for tools that connect to SharePoint using App passwords, as they no longer work due to Microsoft’s security updates. The implementation of security defaults by Microsoft has disrupted the integration process for customers relying on these legacy authentication methods.

To address this issue, the R&D team is working on a New Sharepoint connector which will implement OAuth-based authentication support, to be a future-proof solution. However, this connector is a work in progress and currently is provided with limited capabilities to work with list, and we are working on adding the library API’s.

We also have documented a solution that describes how the authentication policies could be adjusted to restore functionality and maintain seamless integration with the current version of the SharePoint connector.

Continue reading to understand the 2 different paths of resolutions and make a calculated choice.

There are 2 resolutions to this scenario:

A. Adding Conditional Access to specifically allow the connector access to the services

Pro: No Project/code changes required

Con: This feature requires “Entra ID P1 licenses” or higher.

 

B.     Using the new connector that connects to the Sharepoint service using OAuth and therefore working with the new Default Policy

 Pro: Works with the security defaults

Cons: This requires the Project to be adjusted to use the new connector as it is not a snap-in replacement to the original. The connector is new and only limited List Features are implemented.

Library features are still under development with R&D. - This will change in future version.

Using Conditional Access – with current connector [A]

One way of keeping the connector and the project unchanged is to implement “Conditional Access” if your organization has the EntraID P1 license. 
This access policy method provides finer control over the static “security defaults” policy which is a single security default policy applied all across the org.
In this approach the admin can define an App password to work with the specific user that xpi resource is using, ensuring that our product can continue to integrate with SharePoint as we complete the transition to OAuth-based authentication; and adding the MFA requirement policy for all others.

Note: If your org is already using Conditional Access the latter (MFA for other users) is probably already covered.

Key components of this solution:

  • Disable Security Defaults: This step disables Microsoft’s security defaults that prevent legacy authentication methods such as App passwords from being used.

  • Conditional Access Policy: By creating and enforcing conditional access policies, we can selectively allow legacy authentication for specific users, while maintaining a secure environment for the rest of the system.

  • Targeted Legacy Authentication: We will enable legacy authentication only for those users who require it for the integration to function.

Instructions for configuration:

  1. Disable Microsoft Security Defaults: This step is required to allow legacy authentication methods such as App passwords. Ignore this step if already on “Conditional Access” and “Security defaults” disabled.

  2. Configure Conditional Access Policies: Using Microsoft’s Conditional Access policies, specify that legacy authentication should only be enabled for specific users who need it for SharePoint integration.

  3. Enable App Passwords for Specific Users: Generate App passwords for the specific users that require them for integration with SharePoint. These users will be able to authenticate through the App password while we work on updating the product.

Due to security enhancements at Microsoft, the App password option is invisible under users’ account security settings.

Follow these steps to make it visible and create an app password.

Step 1: Configure Azure Entra Conditional Access Policies

  • Access the Azure Entra Admin Centre and Modify the Conditional Access Policy for MFA:

    1. Navigate to Microsoft Entra Conditional Access > Policies.

    2. Locate the Required multifactor authentication policy.

    3. Edit the policy and include the desired user(s) in the Include section.

  • Exclude the User from the Legacy Authentication Policy:

    1. Find the Block legacy authentication policy.

    2. Edit the policy and add the desired user(s) to the Exclude list.

    3. Save the changes to ensure the user is excluded from this policy.

Step 2: Enforce Per-User Multi-Factor Authentication

  • Open Multi-Factor Authentication Settings:

    1. Go to https://admin.microsoft.com

    2. From the left navigation pane, select Users > Active users.

    3. Click on the Multi-Factor Authentication option (located in the ribbon or additional settings).

  • Locate the User:

    1. On the Per-user MFA page, search for the desired user by their name or email address.

  • Enforce Multi-Factor Authentication:

    1. Select the user and click Enforce to enable MFA for them.

    2. Once enforced, the user’s MFA status will change to Enforced.

Step 3: Verify App Password Option

  1. After enforcing MFA, instruct the user to log in to their account.

  2. During the next login process, the user will be prompted to configure multi-factor authentication.

  3. Once MFA is configured, the App Password option will be visible under their account security settings.

By using this solution, customers can continue to integrate seamlessly with SharePoint, while ensuring the security of customers’ systems.

Security Considerations when using “Conditional Access”

Special care should use taken when defining “Condtional access” to avoid any unintended “Security gaps” in you environment:

  • Multi-Factor Authentication (MFA) Enforcement: Although legacy authentication is allowed for specific users, we should continue to enforce Multi-Factor Authentication (MFA) across the organization. This significantly reduces the risk of unauthorized access.

  • MFA for Admins: We strongly recommend enforcing MFA for all administrators. Admin accounts are often targeted by malicious actors, so additional authentication steps help ensure their security.

  • Visibility of App Passwords: App passwords are only visible when they are first generated. After creation, the password cannot be retrieved or seen again. This helps mitigate the risk of unauthorized access by limiting the exposure of the password.

  • Limited Scope of Legacy Authentication: By using Conditional Access policies, we limit the scope of legacy authentication to only those users who need it. All other users are protected by the organization’s overall security protocols, including MFA.

  • Securing the Rest of the System: While legacy authentication is enabled for specific users, all other users and systems remain protected by the Conditional Access policies, ensuring that the overall security of the organization is not compromised.

 

 

In summary, customers can and should secure an environment with enforced MFA, restricted access, and limited visibility of sensitive credentials to maintain the integrity of the customer’s organization’s security posture while allowing the conditional access to the only restricted user for xpi use case.
